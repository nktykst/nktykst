# 理解負債ゼロ原則 (comprehension-kit)

このプロジェクトでは AI に書かせたコードも **人間が自分の言葉で説明できる状態** を保つ。
「動いたが理由は分からない」コードを残すことを理解負債と呼び、発生した瞬間に返済する。

## Claude が常に守ること

1. **変更には台帳エントリ**: コード (機能・バグ修正・設定・依存・アルゴリズム) を変更したら、セッション終了前に `/debrief` で `docs/comprehension/entries/` にエントリを書く。typo やフォーマットのみの変更は不要。Stop フックが未記入を検知してブロックする。
2. **導入には理由**: 新しいライブラリ・パターン・抽象化を持ち込むときは、「なぜそれか」「代替は何か」を一行で必ず言う。「ベストプラクティスだから」は理由にならない。
3. **賢さより明示性**: 説明に 3 文以上かかる技巧 (メタプログラミング、暗黙のブロードキャスト、複雑な内包表記) は避け、素朴な書き方を選ぶ。どうしても必要なら理由をコメントと台帳に残す。
4. **shape と不変条件**: ML / 数値コードでは tensor の shape 遷移、単位、前提 (正規化済みか等) をコメントで書く。
5. **分からないことは分からないと書く**: 自信のない箇所は台帳の Unknowns に正直に書く。取り繕わない。
6. **質問には台帳から**: ユーザーが「これ何?」「なぜ?」と聞いたら、まず台帳エントリ (`ledger.py list --json`) を引き、コードとの食い違いがあれば指摘する。
7. **認知負債の上限**: セッション開始時に未検証エントリが上限 (既定 10) 以上なら、新しい機能を作る前に `/review` を提案する。ユーザーが断れば従うが、提案は必ずする。
8. **説明はユーザーの言葉で**: 専門用語は初出で 1 行定義。「要するに」の一文を入れる。コード全文貼りで説明を代替しない。

## 使えるコマンド

| コマンド | 役割 |
|---|---|
| `/debrief` | 変更を台帳に記録 (What/Why/How/Unknowns/確認問題) |
| `/explain <対象>` | 3 層の解説 + 消したら何が壊れるか + 確認問題 |
| `/review` | 期限到来エントリを、答えを見せずに検証 (間隔反復) |
| `/debt-audit` | 未記録の変更と認知負債量の棚卸し、返済計画 |
| `python3 .claude/comprehension/ledger.py --help` | 台帳 CLI |

台帳の形式は `docs/comprehension/README.md` を参照。

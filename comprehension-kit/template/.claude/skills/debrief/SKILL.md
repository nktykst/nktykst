# /debrief — 変更の振り返りと台帳記入

目的: 今日書いた (書かせた) コードを、ユーザーが **コードを見ずに自分の言葉で再実装できる** 粒度で言語化し、台帳に残す。
「動いた」で終わらせない。動く理由を残す。

## 手順

1. **変更を集める**
   - `.claude/comprehension/.session/*.touched` の最新ファイルと `git diff --name-only HEAD` / `git status --porcelain` を見て、このセッションで触ったコードファイルを列挙する。
   - 論理的なまとまり (機能・バグ修正・設計変更) ごとにグループ化する。1 コミット ≈ 1 エントリが目安。typo やフォーマットだけの変更はエントリ不要。

2. **グループごとにエントリを作る**
   ```bash
   python3 .claude/comprehension/ledger.py new --title "<日本語の短い題>" --slug <english-slug> --files <path> [<path> ...] --source claude-code
   ```
   出力されたパスのファイルを開き、各セクションを埋める。

3. **各セクションの書き方 (ここが本体)**
   - **What**: 入口となる関数/クラス名を必ず書く。「どこから読めば良いか」が分かること。
   - **Why**: 検討した代替案を最低 1 つと、選ばなかった理由。ライブラリ/パターンを新たに導入した場合は「なぜそれか」を必ず一行。
   - **How**: 専門用語は使うたびに 1 行で定義する。数式やアルゴリズムは、入出力の形 (shape, 型) と不変条件を書く。ML コードなら tensor の shape 遷移を明記。
   - **Unknowns**: Claude 自身が確信を持てない箇所 (「動いたが理由が説明しきれない」「エッジケース未検証」) を **正直に** 書く。空にしない。
   - **Failure modes**: どの前提が崩れると壊れるか。
   - **Recall**: 答えを見ずに答えられれば理解している、と判定できる問いを 3 問以上。「〜は何をしているか」より「なぜ〜ではなく〜なのか」「〜を変えたらどこが壊れるか」型を優先。

4. **フェインマン・チェック (対話)**
   エントリを書き終えたら、ユーザーに次を求める:
   > 「この変更を、コードを見ずに 3 文で説明してください」
   ユーザーの説明を聞き、抜けている概念があれば指摘して、エントリの How に追記する。
   ユーザーが不在/スキップした場合は、エントリの status を unverified のままにし、その旨を Unknowns に書く。

5. **最後に**
   `python3 .claude/comprehension/ledger.py stats --brief` を実行して現状を示す。
   未検証が上限 (既定 10 件) を超えていたら、次回セッション冒頭で /review を行うよう提案する。

## 禁止事項
- コードをそのまま貼って説明の代わりにしない。
- 「一般的なベストプラクティスなので」を Why にしない。具体的なトレードオフを書く。
- Unknowns を「なし」で埋めない (本当にないなら、なぜ確信できるかを書く)。
